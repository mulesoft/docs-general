= Agent Fabric Overview
:keywords: mulesoft agent fabric, mcp bridge, mcp connector, enterprise actionability, ai agents, mulesoft integration, model context protocol

Agents, APIs, and MCP servers end up on different platforms, with different security and no shared view of LLM cost. Agent Fabric is the control plane for that landscape: catalog what exists, let agents call systems you already run, enforce shared policy at runtime, and see what those calls cost.


[[how-agent-fabric-works]]
== How Agent Fabric Works

Without a shared control plane, agents stay siloed, policy differs by platform, and LLM spend is hard to track. Use Agent Fabric when those assets span more than one platform and you need one place to discover them, let them call existing systems, and run those calls under shared governance, security, and cost controls.

MuleSoft supports Agentforce and Agent Fabric together. Each plays a distinct role:

* Agentforce
+
Build and deploy Salesforce-native agents for use within the Salesforce ecosystem.
* Agent Fabric
+
Govern, secure, and cost-manage agents across any platform, including Salesforce Agentforce, Amazon Bedrock, Google Vertex AI, Microsoft Copilot Studio, and others. Choose Agent Fabric when you need a single inventory of agents built anywhere, the same security and compliance rules everywhere, or cost control across the agent ecosystem.

Agentforce and Agent Fabric are core components of Salesforce's Agentic Enterprise Architecture. Agent Fabric operates in the orchestration layer, where it coordinates agents across vendors.

image::agent-fabric-pillars.png["Diagram of Agent Fabric: a visibility foundation that supports connecting agents to existing systems, governing production traffic, and controlling LLM cost"]

You can't apply governance, security, or cost controls to agents you haven't found. After you have a complete inventory, choose the job you need to do:

* <<agent-registry,Agent Registry>>
+
Find every agent, MCP server, and API so you reuse what exists instead of rebuilding it, and so later controls have something to apply to.
* <<agent-operations,Agent Operations>>
+
Let agents update records, call APIs, and hand work to other agents, using systems you already run, without a rebuild.
* <<govern,AI Security and Governance>>
+
Put the same authentication, access, and security rules on every agent, MCP server, and LLM call, so production traffic doesn't depend on which platform built the agent.
* <<cost-control,AI Cost Control>>
+
See where token spend goes, cap it, and stop paying a frontier model for work a smaller model can do.

[[agent-registry]]
== Agent Registry

You can't govern, secure, or cost-manage agents you don't know about. The registry is the inventory of every agent, MCP server, and related service, regardless of platform, so reuse and control have a single source of truth.

=== Registry (Exchange)

Teams rebuild agents and tools that already exist because nobody can find them. Portfolio is that catalog in the enhanced MuleSoft experience: Agents, MCP Servers, Model Proxies, APIs, and Gateways, plus a curated set of public MCP servers from the Official MCP Registry and Informatica.

* Find and reuse registered agents, MCP servers, model proxies, APIs, and gateways
* See conformance status and instance health before you depend on an asset
* Govern, monitor, and manage lifecycle from the asset's catalog page
* Publish agent networks and MCP servers so other teams can reuse them

Use the registry when you start a new agentic project and want existing assets first, or when you want to share what your team built.

Learn more: xref:exp-portfolio-overview.adoc[]

=== Scanners

Agents appear on cloud platforms faster than teams can register them by hand. Scanners watch supported providers and add discovered agents, APIs, and MCP servers to the matching portfolio catalog so the inventory stays current.

* Connect cloud providers as scanner sources
* Discover and register agents, MCP servers, and APIs on a schedule or on demand
* See last-run results and how many assets each scan found
* Manage scanners from *Platform* > *Providers*

Use scanners when agents run on more than one platform and manual registration can't keep the registry current.

Learn more: xref:exp-scanners-add-from-providers.adoc[]

[[agent-operations]]
== Agent Operations

An agent that can only describe a problem can't fix it. Agent Operations exposes the APIs, applications, and agents you already run as tools those agents can call, and coordinates multiple agents when one isn't enough, without rebuilding those systems.

Start with MCP Bridge for existing APIs and A2A Bridge for agents that aren't A2A-compliant. Add a broker only when work must span specialized agents. Use connectors, B2B, and IDP when agents need LLMs, trading partners, or data locked in documents.

=== MCP Bridge

Your APIs already do the work agents need, but agents can't call them as tools until you expose them. MCP Bridge converts an API instance into an MCP server through configuration. You pick the operations, keep the API unchanged, and apply the same governance you already use.

* Convert an existing API instance into an MCP server without custom code
* Expose only the operations agents should call
* Apply existing governance policies to the resulting MCP server

Use MCP Bridge when agents must call APIs you already have, and you don't want a custom MCP server.

Learn more: xref:exp-services-create-mcp-server.adoc[]

=== A2A Bridge

Agent Fabric can orchestrate A2A-compliant agents. Many enterprise agents, including Salesforce Agentforce agents, aren't A2A-compliant. A2A Bridge puts an A2A facade in front of those agents so you can discover, govern, monitor, and orchestrate them without rebuilding them.

* Make a non-A2A source agent A2A-compliant through configuration
* Customize the advertised A2A card and skills before publishing
* Deploy the bridge to a managed or self-managed Omni Gateway
* Treat the bridged agent like any native A2A agent in your portfolio

Use A2A Bridge when you need to orchestrate agents that aren't A2A-compliant yet. Use A2A Connector when you need custom Mule application logic or a platform that isn't natively supported.

Learn more: xref:exp-services-create-a2a-bridge.adoc[]

[[agent-broker]]
=== Agent Broker

When several specialized agents must share a request, someone has to decide who does which step. The broker routes each task to the best-suited A2A-compliant agent or broker, tracks task state, and becomes a reusable asset in your portfolio.

You define the broker and its nodes in Agent Script, in a graph that mixes deterministic and non-deterministic steps.

* Delegate tasks to specialized A2A-compliant agents or other brokers
* Define routing in Agent Script
* Deploy the agent network, including the broker, to CloudHub 2.0
* Monitor routing decisions with Agent Visualizer

Use a broker when routing must span multiple specialized agents. Many solutions run with agents and MCP servers alone.

Learn more: xref:agent-network::af-define-your-agent-network-specification.adoc[]

=== Agent Network

A production agentic solution is usually several agents, LLMs, and MCP servers, not one agent. An agent network is the composition you define, deploy, and reuse: which assets work together, how they connect, and which policies apply.

You configure the network in a YAML file. If it uses brokers, you define them and their nodes in Agent Script.

* Define a multi-agent system in one YAML configuration
* Connect agents to backend systems through MCP servers
* Deploy agents, brokers, and MCP servers together
* Register network assets in your portfolio for reuse

Use an agent network when multiple agents, LLMs, or MCP servers must work together. Start with agents and MCP servers. Add a broker only when you need intelligent routing.

Learn more: xref:agent-network::af-agent-networks.adoc[]

=== MCP Connector

When an existing API isn't enough, MCP Connector lets you build the exact tools agents need. You write a Mule application that exposes custom logic, composes multiple systems, or calls external MCP servers, then govern that application like any other agentic asset.

* Build Mule applications that expose tools and resources to MCP clients
* Connect Mule applications to external MCP servers
* Compose multiple backend systems into one MCP server
* Define custom logic for how agent requests are handled

Use MCP Connector when agents need capabilities that don't map to a single existing API.

Learn more: xref:mcp-connector::index.adoc[MCP Connector]

=== A2A Connector

Existing Mule applications can take part in agent networks without becoming native agents. A2A Connector adds A2A support so those applications can receive tasks from a broker and delegate work to other agents.

* Make Mule applications A2A-compliant
* Receive and delegate tasks inside an agent network
* Join broker-coordinated workflows without rebuilding the applications

Use A2A Connector when existing Mule applications must participate as A2A-compliant agents.

Learn more: xref:a2a-connector::index.adoc[A2A Connector]

=== Other AI Connectors

Agents need the LLMs and knowledge stores you already operate. AI Connectors give agentic workflows pre-built access to those models and vector databases so you don't write a custom integration for each one.

* Connect LLMs and vector databases to agentic workflows
* Use existing AI infrastructure inside agent networks
* Give agents organizational context from knowledge stores

Use AI Connectors when agents must reason with LLMs or retrieve context from vector databases you already run.

=== B2B (Partner Manager)

Order-to-cash, procure-to-pay, and logistics flows fail for agents that can't exchange B2B messages. Partner Manager lets agents send and receive those transactions without each agent implementing EDI standards or transport protocols.

* Send and receive B2B transactions with trading partners
* Query message flow status, transmission tracking, and acknowledgments
* Include B2B activity in multi-step agent workflows

Use Partner Manager when agents must exchange B2B messages with external partners.

Learn more: xref:partner-manager::index.adoc[]

=== IDP (Intelligent Document Processing)

Invoices, purchase orders, and similar documents hold data agents need but can't read as-is. IDP extracts that data into structured results agents can act on, with confidence scoring and human review when quality requires it.

* Extract structured data from invoices, purchase orders, and custom document types
* Configure document actions with pre-built or custom schemas
* Apply confidence thresholds and human-in-the-loop review
* Feed extraction results into agent workflows through published APIs

Use IDP when agents must act on data trapped in documents, such as procurement, accounts payable, or order processing.

Learn more: xref:idp::index.adoc[]

[[govern]]
== AI Security and Governance

Agents that reach production without shared security, identity, and policy become a risk: different platforms enforce different rules, or none. These capabilities define one layer and enforce it on live traffic.

=== Omni Gateway

Policies you define only protect production if they run on the request. A managed instance of an API, agent, or MCP server puts Omni Gateway in that path so authentication, rate limits, and access rules apply to every call.

* Require authentication and authorization on agent, API, and MCP server requests
* Limit which tools and APIs an agent can call
* Keep an audit trail of traffic for security and compliance

Use a managed instance on Omni Gateway when agents or APIs handle sensitive data, call external systems, or must follow the same runtime rules in every environment. LLM traffic uses a model proxy, which you also deploy to Omni Gateway.

Learn more: xref:exp-instances-add.adoc[] and xref:exp-policies-apply-manage.adoc[]

=== Governance Strategies

Rewriting the same security, privacy, and cost rules for every agent and service doesn't scale. A governance strategy defines those rules once and applies them across the agents, MCP servers, APIs, and model proxies in scope.

* Define rules once for access, data privacy, performance and cost, and compliance
* Apply them at the service or instance so live traffic matches the strategy
* See which services fail conformance and which have no strategy
* Block or flag non-compliant actions at design time or runtime

Use governance strategies when a portfolio of agents and services must follow the same auditable rules.

Learn more: xref:exp-governance-work-with-strategies.adoc[]

=== Universal Policies

On a multi-vendor gateway landscape, the same control is a different native policy on each platform, so gaps appear. Universal Policies let you author the intent once. Agent Fabric translates it for each gateway.

* Author a policy once and apply it across gateways from multiple vendors
* Enforce common controls such as API key enforcement, CORS, header manipulation, IP allowlisting, and JWT validation
* Keep the same governance as services move or scale across platforms

Use Universal Policies when you run gateways from more than one vendor and need the same controls on all of them.

Learn more: xref:exp-policies-universal.adoc[]

=== Cross-Gateway and Third-Party API Governance

Services that run on a gateway you don't manage in Anypoint still have to meet your standards. Cross-gateway governance includes those APIs in the same conformance view so they don't escape oversight.

* Govern third-party APIs alongside Anypoint-managed services
* Monitor conformance across gateways from different vendors
* Find services that have no active governance strategy

Use cross-gateway governance when business-critical services run outside Anypoint and still need to meet your standards.

Learn more: xref:exp-governance-govern-third-party-apis.adoc[] and xref:exp-governance-monitor-cross-gateway-conformance.adoc[]

=== Model Proxy

Agents that call each LLM provider directly get a different endpoint, a different policy set, and a different bill. A model proxy, deployed to Omni Gateway, is one governed endpoint for multiple providers. Routing, caching, and policy run in front of every call. Token data from those calls feeds cost management.

* Give agents one governed endpoint for multiple model providers
* Route by model or by meaning so simple tasks don't always hit the most expensive model
* Reuse similar responses with semantic caching to cut latency and spend
* Apply policies, including the security policies that detect and contain rogue agents

Use a model proxy when agents call LLMs and you need the same governance, routing, and cost visibility across providers.

Learn more: xref:model-proxy.adoc[]

=== Security

A compromised, misconfigured, or malicious agent can leak data, take unauthorized actions, or drive unexpected cost. These controls detect that behavior, keep credentials in the vault you already use, and surface known risk on services you've already discovered.

* Detect and contain rogue agents: Spot anomalous agent traffic and contain a rogue agent before it causes damage. Apply the Rogue Agent Detection policy to flag risky behavior for your review. The Agent Kill Switch policy blocks that agent's access when you choose to quarantine it. Quarantine always requires your review, and you can reverse it. For more information, see xref:exp-detect-and-contain-rogue-agents.adoc[].
* External vaults: Keep API keys in the secrets manager your organization already uses, such as AWS Secrets Manager, Azure Key Vault, or HashiCorp Vault, and let model proxies authenticate with those credentials at runtime without copying secret values out of the vault. For more information, see xref:exp-vaults-manage.adoc[].
* Akamai risk correlation: Surface shadow APIs and known risk on the services you already discovered, so you can triage exposure before it becomes an incident. For more information, see xref:exp-akamai-risk-correlation.adoc[].

=== Trusted Agent Identity

* What it is: Trusted Agent Identity is a set of identity and authorization policies that ensure agents act with a specific user's identity and proper authentication on every interaction, so access follows the calling user's permissions rather than granting blanket agent access.
* Role in Agent Fabric: Without identity controls, agents can become a governance gap, calling systems with elevated or opaque permissions that bypass the controls applied to human users. Trusted Agent Identity closes that gap, ensuring every agent interaction is authenticated, attributable, and auditable. This is what makes agent governance meaningful in regulated environments.
* What you can do:
** Ensure agents act under a specific user's identity rather than with generic or elevated agent-level access
** Keep every agent action authenticated and attributable to the user who initiated it
** Maintain a complete audit trail of agent actions tied to real user authorization

* When you need it: Use Trusted Agent Identity any time agents call APIs or services on behalf of users, or when compliance requires knowing not just that an agent made a call, but who authorized it.

[[cost-control]]
== AI Cost Control

LLM token spend grows whenever agents default to an expensive model, repeat similar calls, or send more payload than the model needs. Budget management shows that spend and caps it. Cost optimization reduces what each call consumes.

=== Budget Management

Cost Management, under *Governance* > *Cost Management* in the enhanced experience shows token usage and spend across your portfolio so you can see where cost goes and cap it. Set model costs so token counts read as dollars, set budgets to limit spend or tokens over time, and use model wallets to cap a caller's token or dollar spend against a provider.

* Monitor token usage and spend across model proxies, agents, and MCP servers
* See which providers and model wallets are at risk or at their limit
* Set input and output token costs per model so reports read as dollars
* Set daily, weekly, or monthly budgets by spend or by tokens
* Cap a model-proxy caller's token or dollar spend against a provider. A wallet matches the system-generated client ID and the JWT claims you define, then the proxy blocks further requests to that provider's models after the budget is reached.

Use budget management when you need visibility and limits on LLM spend. Model wallets require an identity provider. Budgets are approximate: usage can briefly exceed a limit before the proxy blocks requests.

For more information, see:

* xref:exp-governance-view-cost-and-token-usage.adoc[]
* xref:exp-model-wallets-manage.adoc[]
* xref:exp-models-manage-costs.adoc[]

=== Cost Optimization

A frontier model for a simple task, a repeated prompt, or a bloated payload all add cost without adding value. Optimization policies and routing run on the model proxy so you send fewer tokens and the right-sized model, without changing agent behavior.

* Route by model or by meaning (semantic routing) instead of always using the most expensive model
* Reuse results for similar requests with semantic caching in your own vector database
* Trim unnecessary tools and payload with optimization policies such as MCP tool mapping, progressive disclosure, payload cleanup, structure compression, and clean responses

Use cost optimization when token consumption is a significant cost and you want to reduce spend without degrading results.

For more information, see:

* xref:model-proxy-semantic-service.adoc[]
* xref:model-proxy-semantic-caching-service.adoc[]
* xref:exp-governance-view-cost-and-token-usage.adoc[]

[[observe]]
== Observe

You can't tell whether governance and cost controls are working if you can't see what agents are doing. Observability shows structure, live traffic, and health so you can trace a failure, catch a regression, and confirm that policy is in effect.

=== Agent Visualizer

Multi-agent systems are hard to operate when you can't see how work moves. Agent Visualizer maps your agents, MCP servers, and LLMs, including agents from external platforms, so you can verify routing in development and find bottlenecks and failures in production.

* See how agents, brokers, and MCP servers connect
* Watch live request flows and metrics such as latency, throughput, and error rates
* Compare historical patterns when a failure isn't obvious in real time

Use Agent Visualizer during development to verify the network, at deployment to confirm routing, and in production to troubleshoot.

Learn more: xref:agent-visualizer::index.adoc[]

=== Monitor

Defined policy isn't the same as healthy traffic. Monitoring shows latency, error rates, and request volume at the service and organization level so you can catch regressions and decide when to change policy or capacity.

* View runtime health metrics, including time series, on each service's Monitoring tab
* Compare signals across instances or environments to attribute changes to deployments or policy updates
* Route API and runtime alerts to Slack, email, or other channels your team already watches
* Use organization-wide dashboards and reports in Observability, filtered to a service, environment, or route

Use monitoring during development to validate performance, and in production to meet SLAs and catch issues before they affect users.

Learn more: xref:exp-services-monitoring.adoc[]
