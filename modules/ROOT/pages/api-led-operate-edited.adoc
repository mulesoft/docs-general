In this final step, you'll learn how to monitor your deployed API using Runtime Manager - your operations dashboard for CloudHub applications.

== What You'll Learn

* How to view application health and metrics
* How to access application logs
* How to understand Runtime Manager's dashboard

== Access Runtime Manager

. From Anypoint Platform, navigate to Runtime Manager:
+
link:https://anypoint.mulesoft.com/cloudhub/#/console/home/applications["Go to Runtime Manager^", role="button-primary"]

. Ensure you're viewing the *Sandbox* environment.

. Click your *hello-world-impl* application.
+
The dashboard opens.

== View Application Health

The dashboard shows real-time metrics:

* *Status*: Running (green) means your API is healthy
* *Uptime*: How long the application has been running
* *CPU Usage*: Current CPU utilization
* *Memory Usage*: Current memory consumption
* *Replicas*: Shows 1/1 (1 running replica out of 1 expected)

Send a few test requests from Postman and watch the *Message Rate* graph update.

== View Application Logs

Logs help you troubleshoot and understand what your application is doing.

. In Runtime Manager, click *Logs* in the left menu.

. You'll see recent log entries.

. Send a request to your API from Postman.

. Refresh the logs to see your Logger message:
+
[source,text]
----
INFO  [hello-world-impl].get:\greeting
  Received request for greeting
----

. Use log filters:
+
* *Priority*: Filter by INFO, WARN, ERROR
* *Search*: Find specific text
* *Time Range*: View logs from the last 30 days

. Logs show every request, error, and Logger message from your application.

== Understand Your Application's URL

Your application URL has this structure:

[source,text]
----
https://hello-world-impl-jsmith.<space-domain>.cloudhub.io/api/greeting
----

* `hello-world-impl-jsmith`: Your unique application name
* `<space-domain>`: Your Shared Space's domain
* `/api/greeting`: Your API endpoint path

This URL is publicly accessible and automatically includes:

* HTTPS/TLS encryption
* Load balancing across replicas
* DDoS protection
* Automatic scaling

== Test from Anywhere

Your API is now accessible from any device:

* Test from your phone's browser
* Share the URL with teammates
* Call it from other applications
* Use it in front-end web apps

Try it! Open a browser on any device and visit:

[source,text]
----
https://your-app-url.cloudhub.io/api/greeting
----

You'll see your greeting in the browser.

== Monitor Application Health

=== Step 5.1: Review the Dashboard

. In Runtime Manager, click the *customer-order-status-impl* application.
+
The application dashboard opens, showing real-time metrics.
+
image::runtime-manager-dashboard.png[Runtime Manager application dashboard]

. Review key metrics:

* *Status*: Running, Stopped, or Deploying

=== Step 5.2: Check Application Logs

Logs provide detailed information about application behavior and errors.

. In the application details, click *Logs* in the left navigation.
+
The logs panel displays recent log entries.
+
image::runtime-manager-logs.png[Application logs panel]

. Use the log filters:
+
* *Priority*: Filter by log level (INFO, WARN, ERROR, DEBUG)
* *Search*: Enter text to find specific log entries
* *Time Range*: Select custom date ranges (up to 30 days)

. Generate some traffic to see new logs:
+
.. Send requests to your API using Postman
.. Refresh the logs panel
.. Observe the log entries for each request

. Look for your Logger component messages:

[source,text]
----

  Customer Response: {"orderId":"ORD-12345", ...}
----

. Check for errors:
+
.. Filter logs by *ERROR* priority
.. Review any error messages
.. Note the timestamp and context for troubleshooting

== Scale Applications

=== Step 5.5: Adjust Replica Count

For production workloads, you can scale applications horizontally by adding replicas.

. In the application details, click *Settings*.

. Locate the *Replicas* section.
+
image::runtime-manager-replica-settings.png[Replica configuration settings]

. For production scenarios, you might increase replicas:
+
.. Click *Edit*
.. Change *Number of Replicas* from 1 to 2
.. Click *Apply*
+
CloudHub 2.0 performs a rolling update to add the new replica.

. Monitor the scaling operation:
+
.. Return to the *Dashboard*
.. Watch the *Replicas* indicator change from 1/1 to 2/2
.. Traffic automatically load balances across replicas

. For this tutorial, you can leave the replica count at 1 to conserve resources.

=== Step 5.6: Adjust Replica Size

For memory-intensive applications, increase the replica size.

. In *Settings*, locate the *Replica Size* dropdown.

. Available sizes:
+
* 0.1 vCores (0.5 GB RAM) - Tutorial and light workloads
* 0.2 vCores (1 GB RAM) - Low-volume production
* 0.5 vCores (1.5 GB RAM) - Medium-volume production
* 1.0+ vCores - High-volume production

. For this tutorial, 0.1 vCores is sufficient.

=== Step 5.8: Test Rate Limiting

. Open Postman and create a collection with your API request.

. Run the collection repeatedly (send 10+ requests quickly).

. After exceeding the rate limit (100 requests per minute), observe:
+
* HTTP status code 429 (Too Many Requests)
* Response headers showing rate limit information:
+
[source,text]
----
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1234567890
----

. Wait one minute and try again - the rate limit resets.

== Set Up Alerts

Proactive monitoring requires alerts when issues occur.

=== Step 5.9: Configure Application Alerts

. In Runtime Manager, click your application.

. Click *Alerts* in the left navigation.

. Click *Create Alert* to add a new alert rule.

. Configure a CPU alert:
+
* *Alert Name*: High CPU Usage
* *Severity*: Warning
* *Condition*: CPU usage exceeds 80%
* *Subject*: Send email to your address
* *Message*: "Application CPU usage is critically high"

. Click *Create*.

. Create additional alerts for:
+
* Memory usage exceeds 80%
* Application deployment fails
* Application stops unexpectedly
* Response time exceeds 5 seconds

. Test an alert by intentionally triggering the condition (if time permits).

== Best Practices for Production

=== Step 5.14: Production Readiness Checklist

Before moving APIs to production, verify:

*Security*

* [ ] API keys or OAuth tokens configured
* [ ] HTTPS enforced for all endpoints
* [ ] Rate limiting policies applied
* [ ] IP whitelist configured (if needed)

*Reliability*

* [ ] Multiple replicas configured for high availability
* [ ] Appropriate replica size for workload
* [ ] Health check endpoints defined
* [ ] Circuit breakers implemented for downstream calls

*Monitoring*

* [ ] Alerts configured for critical issues
* [ ] Log retention meets compliance requirements
* [ ] Analytics dashboard reviewed regularly
* [ ] Performance baselines established

*Documentation*

* [ ] API specifications published to Exchange
* [ ] Consumer documentation available
* [ ] SLA commitments documented
* [ ] Support contacts identified

== Troubleshooting Common Issues

=== Step 5.15: Resolve Common Problems

*Application Won't Start*

. Check logs for errors during startup
. Verify `pom.xml` configuration is correct
. Ensure all dependencies are available
. Check for port conflicts in configuration

*High Response Times*

. Review logs for slow operations
. Check external service dependencies
. Analyze DataWeave transformations
. Consider increasing replica size

*Memory Errors*

. Increase replica size in Settings
. Review code for memory leaks
. Check payload sizes (large messages)
. Enable object store for caching

*Connection Refused Errors*

. Verify upstream API is running
. Check firewall rules in Shared Space
. Verify correct URLs in configuration
. Test connectivity with curl
