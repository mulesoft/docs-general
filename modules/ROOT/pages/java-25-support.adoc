Upgrading to Java 25 has no immediate impact to Mule applications that are running on Mule versions that support Java 17. However, it is best to start your upgrade planning now. Java 25 upgrade planning includes evaluating integration apps, connectors (Anypoint connectors and custom connectors), Mule Gateway policies, and API proxies, as all of these components rely on Java.

Existing Java 17 apps continue to run on Java 17 until the end of extended support for the Mule version they are running on is reached.

== Steps for Upgrade

// Drafted by analogy to the Java 17 upgrade steps. Pending SME confirmation: minimum versions for Studio, Mule Maven plugin, connectors, and policies, and any Java 25-specific steps.
Follow these steps to upgrade to Java 25:

* *Pre-Upgrade*
. Review your current setup to identify what needs upgrading or removal, such as any Java features that are no longer supported or are marked as deprecated in Java 25.
. Create a comprehensive upgrade plan, including testing, rollback strategies, and post-upgrade checks.
. For on-premises deployments (as with any upgrade), schedule downtime and inform stakeholders to minimize business disruption.
* *Upgrade*
. Upgrade to <<mule-runtime, Mule runtime 4.14>> or later.
. Upgrade all Anypoint Connectors and modules, and custom connectors, used within Mule apps and policies to versions that support Java 25. Connectors that contain custom Java code need additional modifications to ensure compatibility with Java 25.
. Upgrade your policies. Policies that contain custom Java code need additional modifications to ensure compatibility with Java 25.
. Upgrade your API proxies and Mule apps. Proxies that contain custom Java code need additional modifications to ensure compatibility with Java 25.
. Upgrade Anypoint Studio to a version that supports Java 25, and change the target JVM at the Studio project level.
. Test your apps in a controlled environment before going live.
. If you use the Mule Maven plugin to deploy your apps, configure the deployment to use Java 25.
* *Post-Upgrade*
. Monitor your apps for any unexpected behavior.
. Update any relevant documentation to reflect changes made during the upgrade.

[IMPORTANT]
To ensure your API proxies or Mule apps are protected when upgrading, upgrade your policies _before_ upgrading your API proxies or Mule apps.

== Anypoint Connectors and Modules

Before you run apps on Java 25, make sure every connector and module they use supports it. Connector Java compatibility is declared in the `supportedJavaVersions` attribute of the connector's `mule-artifact.json`. In Exchange, connectors that declare Java 25 support are tagged accordingly. To build or update a connector that supports Java 25, use Mule Extension Plugin 1.9.0 or later and declare Java 25 in `supportedJavaVersions`. [[custom-connectors]]
== Custom Connectors

Custom connectors (including custom configuration properties providers) are any connectors that are not developed and maintained by MuleSoft, including connectors that are built by MuleSoft partners or customers. If you are using a custom connector in your app, you must update it to support Java 25 and declare that support in its `supportedJavaVersions` attribute. Apps that use a connector declaring Java 25 support must run on Mule runtime [4.14 or later – confirm; 4.6.22+ / 4.9.9+ for earlier lines].

[[dataweave]]
== DataWeave

DataWeave uses Java's reflection API to read and write Java objects. Java 25 continues to restrict encapsulation and reflective access for the Java Data Format and Mule objects, as in Java 17. [Confirm.]

To ensure your applications continue to work as expected, follow these guidelines:

* Verify that the objects your application uses are Plain Old Java Objects (POJOs) with a default constructor, getters for all properties, and setters for all properties. [Confirm the DataWeave version and whether Java 25 adds requirements.]
* Verify that predefined variables are accessed through their proper API, for example `error.errorMessage` instead of `error.muleMessage` and `error.childErrors` instead of `error.errors`.

For more information, see the following documentation:

* xref:dataweave::dataweave-formats-java.adoc#java-support[Java Format]
