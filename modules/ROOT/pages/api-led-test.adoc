= Step 4. Test the API
:description: Learn how to test your API-led connectivity implementation in MuleSoft, ensuring each API layer functions correctly before deployment.
:keywords: api-led connectivity, api testing, mulesoft testing, anypoint platform, integration testing, api validation, unit testing
:page-pagination:

Test your API locally before deploying it to the cloud. You run the API in Anypoint Code Builder, send requests using Postman, add logging to track requests, and use the built-in debugger to inspect the Mule message at each step.

== Step 4.2: Add Logging

Logging helps you see what's happening inside your flows.

. Click the *Logger* component and configure it:
+
* *Message*: Click *fx* to switch to expression mode, then enter:
+
[source,dataweave]
----
#["Received greeting request for name: " ++ (attributes.queryParams.name default "not provided")]
----
+
This message logs the `name` query parameter value or "not provided" if it's missing.
* *Level*: INFO
+
image::api-tutorial-logger-component-configured-acb.png["Logger component configuration panel showing Message field set to payload and Level field set to INFO"]
. Save your changes.

== Step 4.3: Test with Logging

. Start your application by clicking image:icon-start-debug.png[alt="","",15,15] (*Run*) in the debug toolbar.
. Open the Terminal panel to see your application logs:
+
* Mac: `Cmd+\` or select *View* > *Terminal*
* Windows: `Ctrl+\` or select *View* > *Terminal*
+
[NOTE]
Logger output appears in the Terminal panel, not the Output panel. The Terminal shows the live Mule runtime log as requests are processed.

. Send a request with Postman:
+
[source,text]
----
http://localhost:8081/api/greeting?name=World
----
+
image::api-tutorial-send-postman-request.png[Postman UI with the request URL entered]

. In the Terminal panel, you'll see a log entry similar to:
+
[source,text]
----
INFO  [hello-world-impl].get:\greeting  Received greeting request for name: World
----

. Send a few more requests and watch the logs update.

. Click image:icon-stop.png[alt="","",15,15] (*Stop*) when done.

== Step 4.4: Understanding APIKit Validation

APIKit automatically validates incoming requests against your API specification. Since your API spec defines the `name` query parameter as required, APIKit:

* Validates that the `name` parameter is present before routing to your implementation flow
* Returns a `400 Bad Request` error automatically if the parameter is missing
* Ensures your flow only executes with valid requests that match the API contract

Try it:

. Start the application.
. In Postman, send a request without the name parameter:
+
[source,text]
----
http://localhost:8081/api/greeting
----
. Observe that APIKit returns an error response before your flow executes.
. Check the Terminal â you won't see your Logger message because APIKit blocked the invalid request.

This automatic validation is one of the key benefits of using APIKit â you don't need to write manual validation code for contract requirements defined in your API specification.

== Step 4.5: Use Breakpoints for Debugging

Breakpoints pause execution so you can inspect the Mule message at a specific point in your flow.

. In the canvas, select the context menu for the *Logger* component, and then select *Add Breakpoint*.
+
image::api-tutorial-logger-context-menu-acb.png[The context menu for the Logger component with an arrow pointing to the Add Breakpoint option]
+
A red dot appears, which represents a breakpoint.
+
image::api-tutorial-logger-breakpoint-acb.png[The Logger component with a red dot representing a breakpoint]

. Click image:icon-run-debug.png[alt="","",15,15] (*Run and Debug*) in the activity bar to open the Run and Debug panel.

. Select *Debug Mule Application* to start your application in debug mode.
+
image::api-tutorial-debug-option-acb.png[The Debug Mule Application option selected in the Run and Debug panel]
. Send a request from Postman:
+
[source,text]
----
http://localhost:8081/api/greeting?name=World
----

. Return to Anypoint Code Builder.
+
Execution pauses at the breakpoint. The debug toolbar appears at the top of the editor, and the *Variables* panel appears in the Run and Debug panel.
+
[NOTE]
The Variables panel is in the *Run and Debug sidebar*, not at the bottom of the IDE. If you don't see it, make sure the Run and Debug panel is open (image:icon-run-debug.png[alt="","",15,15] icon in the activity bar).

. In the *Variables* panel, expand *Mule Message* to inspect:
+
* *payload*: The current message content
* *attributes*: HTTP request details, including headers, query parameters, and URI
* *vars*: Any flow variables set during execution
+
image::api-tutorial-debug-panel-variables-acb.png[The Variables panel in the Run and Debug panel]

. Click *Continue* in the debug toolbar to resume execution and complete the request.

. Click image:icon-stop.png[alt="","",15,15] (*Stop*) when done.
