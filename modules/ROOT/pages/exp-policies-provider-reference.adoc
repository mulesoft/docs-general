= Provider Support and Limitations for Policies
:keywords: policy provider support, apigee, azure api management, kong, aws, injection points, policy permissions, anypoint platform

External gateways differ substantially in what they support and how they behave. This reference summarizes per-provider policy support, the setup each provider requires on your side, injection points, and locking behavior during operations.

== Before You Begin

Before getting started, make sure you have:

* An Anypoint Platform account.
* A connected scanner for each external provider whose policies you want to manage. Policy management reuses the scanner connection's credentials. See xref:exp-scanners-add-from-providers.adoc[].

== Per-Provider Permissions

Because policy management reuses the scanner connection, the permissions you see reflect what that connection's identity is allowed to do on the provider, not a separate login.

* Google Apigee: The enhanced MuleSoft experience checks the connected Google service account's actual permissions on Google Cloud. See <<apigee-required-permissions-and-roles>>.
* Azure API Management: The enhanced MuleSoft experience checks the connected Azure principal's role-based permissions on the API resource, including permissions inherited from higher scopes.
* Kong Gateway: access is based on your Kong Konnect roles and team memberships for the instance's control plane. Admin and power teams get full access; otherwise a matching role is required.
* Omni Gateway: uses the same Anypoint Platform permissions as elsewhere in the product, with no separate provider-side check.
* Amazon API Gateway: The enhanced MuleSoft experience reuses the scanner connection's AWS credentials. The connected AWS account must have permission to read, change, and deploy the API. A connection that can scan the API may still lack permission to change policies. Cross-account connections using a hub role are not supported for policy writes.

== Injection Points

An injection point is where a policy runs relative to the request and response. Each policy template declares the injection points that it allows. If you choose an unsupported injection point, the system rejects the choice.

* Google Apigee: you can choose request or response. On the Apigee side, both map to the proxy-level `PreFlow` (request and response map to the corresponding `PreFlow` section).
* Azure API Management: supports `inbound`, `outbound`, and `backend`. Azure's error-handling section is not editable through the enhanced MuleSoft experience.
* Kong Gateway: the injection point is informational only; Kong's plugin phase is fixed, so it doesn't change placement.
* Amazon API Gateway: placement answers "which part of the traffic does this policy affect?" For example, header mapping can add request or response headers to a selected operation. See <<aws-specific-behavior>>.

[[instance-locking-during-operations]]
== Instance Locking During Operations

To prevent conflicting concurrent changes, an in-progress operation takes a lock. The scope of that lock differs by provider:

* Azure API Management, Google Apigee, and Amazon API Gateway lock the entire API instance. While one policy operation is running, no other policy operation on that instance can start. Wait for the running one to finish. On Azure, an instance's policies live in a single document, so any change touches the whole thing. On Apigee, a change re-deploys the whole proxy, so it's inherently instance-wide. On Amazon API Gateway, a policy change deploys the entire API configuration to the selected stage, even when the policy targets only one path or method.
* Kong Gateway locks only the specific policy that you modify. You can work with other policies on the same instance simultaneously.
* Omni Gateway takes no such lock.

If an operation is already in progress, another operation is mid-flight on that instance (Azure, Apigee, or Amazon API Gateway) or on that same policy (Kong). Wait for the operation to complete. You can track it in the *Activity log*. See xref:exp-policies-activity-log.adoc[].

[[apigee-required-permissions-and-roles]]
== Apigee Required Permissions and Roles

For Apigee, the connected Google service account requires these permissions for policy create, edit, and remove operations to work. They cover the read-import-deploy cycle every Apigee change performs:

* `apigee.proxies.get`
* `apigee.proxyrevisions.get`
* `apigee.proxies.create`
* `apigee.deployments.list`
* `apigee.deployments.create`

To get these permissions, you can use one of these predefined Apigee roles:

* Apigee API Admin
* Apigee Environment Admin

Any custom role or higher-scope grant that includes the five permissions also works. The enhanced MuleSoft experience checks the account's effective permissions, not the role name.

[[aws-specific-behavior]]
== Amazon API Gateway Specific Behavior

Amazon API Gateway (REST APIs) policy write support includes policy apply, edit, and remove, with targets below the whole API instance.

=== Setup and Prerequisites

Before writing policies for Amazon API Gateway, ensure that your configuration meets these requirements:

* Use REST APIs, as HTTP APIs aren't supported for policy writes
* Deploy the API stage that you want to change
* Select the specific stage in your configuration
* Use single-account connections, as cross-account connections with a hub role aren't supported
* Grant the connected AWS account permissions to read, change, and deploy the API, because scanning permissions alone don't allow policy changes

=== Policy Scopes

When applying a policy, you can target different scopes:

* *INSTANCE*: all paths and methods in the selected stage.
* *PATH*: all methods at one path, such as `/orders`.
* *METHOD*: one HTTP method across paths, such as `GET`.
* *OPERATION*: one method at one path, such as `GET /orders`.

Supported scopes depend on the policy. To change a policy target, remove the policy and reapply it with the new target.

The target picker uses paths and methods from the API specification. If a route is missing from the specification, update the specification to match your AWS API before you apply the policy.

A policy can have a specific path or method and still be editable. It becomes read-only when the enhanced MuleSoft experience can't safely manage its settings or target.

=== Deployment and Failures

Applying, editing, or removing an AWS policy deploys the entire API configuration to the selected stage. Keep these impacts in mind:

* Other pending changes in AWS also deploy, even when the policy targets only one path.
* CORS and Header Mapping rebuild the API configuration from the deployed version of the selected stage. This can overwrite undeployed changes and affect other settings such as API keys or caching.
* Before you apply a policy, review pending changes in AWS.

If an operation fails after you change the configuration in the AWS Management Console but before deployment, the stage sometimes continues running its previous version. Failed operations don't automatically undo changes made in AWS.

To recover after a failed operation:

. Check the *Activity log* tab for details.
. Compare the AWS Console configuration with the version deployed to the selected stage.
. Resolve any differences.
. Rescan to refresh the enhanced MuleSoft experience view.
. Retry the operation.

Rescan refreshes the enhanced MuleSoft experience view without deploying or undoing changes. Rescan also after:

* Changing a managed policy or its target.
* Deleting or reordering IP filtering rules in AWS.
* Correcting a failed operation or when a successful change is missing from the enhanced MuleSoft experience.

=== CORS Behavior

* Open CORS applies to currently deployed paths that have a method other than OPTIONS. Paths added later don't automatically receive the policy.
* CORS adds or updates the OPTIONS method used for browser preflight requests. If an existing OPTIONS method has a custom configuration that the enhanced MuleSoft experience can't manage, the operation is blocked.
* AWS supports one allowed origin. AWS rejects multiple origins, as well as `*` when credentials are allowed.
* For Lambda or HTTP proxy integrations, the backend requires CORS response headers. A successful preflight alone doesn't guarantee that the browser can read the response.
* The entire API shares optional CORS headers for default client (4xx) and server (5xx) errors. Setting them from another path can replace earlier values. Turning off the option or removing a path's CORS policy doesn't clear those shared headers.
* Custom CORS configurations are sometimes read-only. CORS and Header Mapping changes are blocked while the selected stage uses a canary deployment to prevent conflicts during the staged rollout.

=== Header Injection Behavior

* Open Header Injection maps to AWS Header Mapping and adds headers with fixed values to requests or responses.
* The target method and integration must already exist. Lambda or HTTP proxy integrations aren't supported, along with ANY, OPTIONS, or CONNECT targets.
* If the same header is already configured, the operation fails instead of overwriting it.
* Configure Access-Control headers through CORS instead.
* Header names must be valid and unique (ignoring case). Values can't contain line breaks or single quotes.
* For responses, the supported form uses the same header value across response codes. Custom or incomplete mappings are sometimes read-only.
* The platform hides sensitive values after scanning, and policies with hidden values are read-only. A hidden value doesn't mean the header is absent.

=== IP Filtering Behavior

* Native IP filtering lets you allow or deny requests based on source IP address. An allow rule permits matching requests, and a deny rule blocks matching requests.
* Open IP Allowlist adds an allow rule and keeps existing AWS rules. Existing allow and deny rules still affect access. Adding this policy alone doesn't guarantee that every unlisted address is blocked.
* IPv4 and IPv6 addresses and ranges are supported. Private API endpoints aren't supported because they require a different method to identify the caller's original IP address.
* Paths with parameters, such as `/orders/{id}` or `/{proxy+}`, use AWS wildcard matching and sometimes match more routes than intended. Check the resulting target after scanning.
* Editing or removing a policy changes its scanned rule and keeps other rules. Reordering or deleting rules directly in AWS can change how the enhanced MuleSoft experience identifies remaining rules. Rescan before you edit another affected policy.
* The entire AWS resource policy has an 8,192-character limit. A small addition can fail if the policy is already close to that limit.
